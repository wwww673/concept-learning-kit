1. 学习目标

  2. 能画出 Agent 的基本运行循环，并标出每一步输入了什么、输出了什么。
  3. 能判断一个具体任务该不该上 Agent，并给出至少两条反对或支持的理由。

2. 核心问题

  • Agent 和普通「大模型对话」的本质差别，是模型变强了，还是系统结构变了？
  • 为什么 Anthropic 强调 Agent 每一步都要从环境里拿到 ground truth？拿不到会怎样？
  • 什么情况下「上 Agent」是过度设计？

3. 核心机制与组成

Anthropic 在工程博客《Building effective agents》里给了一个很克制但很关键的定义：他们把所有这类系统统称 agentic systems，然后在其中划出一条架构上的分界线——

  • Workflow（工作流）：LLM 和工具通过预先写好的代码路径编排，每一步做什么由开发者定死。
  • Agent（智能体）：LLM 自己动态决定执行流程和工具用法，掌控任务如何完成。

所以 Agent 的「组成」可以拆成五块：

组成部分作用缺了会怎样
模型（大脑）做判断：下一步干什么、用哪个工具、够不够格交差退化为固定脚本
工具（手脚）读文件、跑代码、搜网页、调 API，让模型能影响外部世界只能「说」不能「做」
环境反馈（感官）工具返回的结果、报错、测试通过与否，即所谓 ground truth模型陷入自我想象，无法纠错
循环（生命力）把上面三件事串起来反复执行，直到达成目标退回单轮问答
停止条件（刹车）最大迭代次数、人工检查点、护栏成本失控、错误复合放大

用一行伪代码概括就是：

while not done: 思考 → 选工具 → 执行 → 观察结果 → 更新判断

Anthropic 特别提醒：Agent 的自主性带来更高成本，也带来错误复合（compounding errors）的风险，所以建议先在沙盒里充分测试并配好护栏。

4. 最小心智模型

类比：一个带着工具箱、可以随时来问你的实习生。

你交代目标（「帮我把这批笔记整理成网页」），他不会一步到位，而是先列个待办，动手做一段，看看做出来的东西对不对，不对就改，中途拿不准会回头问你，做完了把结果交给你验收。

普通对话式 AI 更像你问他一句他答一句的顾问——不主动开工，也不对结果负责。这个差别不在智商，而在「他被允许反复动手并根据结果调整」。

5. 我的理解

（本人改写，非 AI 原文）

类比：Agent 不是「更大的大脑」，而是「给同一个大脑配了手、眼睛和重试的机会」。就像同一个厨师，站在只能说话的咨询窗口前，和站在能自己开火、尝味、重做的灶台前，产出完全不是一回事。

大白话：Agent = 大模型 + 工具 + 循环 + 环境反馈。四个要素缺一个都不成立；其中「循环」和「反馈」最容易被忽略，但它们才是让模型从「会说」变成「会做」的关键。

它其实不是：

  • 不是「更聪明的模型」。底层模型没换，换的是系统结构。同一代模型，套上循环和工具就能做单轮做不到的事。
  • 不是「给它一句话它就能全自动搞定」。它需要在关键节点拿 ground truth，也需要停止条件和人工检查点，否则会一直转圈或越错越远。
  • 不是「越自主越好」。Anthropic 的原话是：只在复杂度能被证明带来收益时才加复杂度。我认同这点——能用固定流程解决的，硬上 Agent 是给自己找麻烦。

6. 具体应用场景

场景：按一个 issue 描述，自动修改代码仓库并通过测试

这是 Anthropic 在文中明确列举的 Agent 用例：处理 SWE-bench 类任务，即根据任务描述修改多个文件。

维度内容
谁在用开发者、以及各类 coding Agent 产品
具体怎么用给出 issue → Agent 自己定位相关文件 → 改代码 → 跑测试 → 看报错 → 继续改 → 全绿后提交
为什么非它不可改几个文件、要改几轮，事先无法预知，没法写死一条固定流程；而测试结果提供了明确的 ground truth，让每一步都能被验证
效果怎么衡量任务完成率、平均迭代轮数、token 成本、引入新 bug 的比例

我自己的一个实例：这次作业里，我让 WorkBuddy 帮我建仓库、写文件、跑 git 命令。它之所以能做，正是因为它有文件系统和命令行这两个「工具」，并且能看到每次命令的输出（比如端口被拒、命令不存在）来调整下一步——换成纯聊天窗口，它只能告诉我「你可以执行 git init」，而做不了。

7. 易混淆概念与使用边界

混淆对象表面相似点本质区别判断口诀
Workflow 都在调 LLM、都在用工具、都能完成多步骤任务 Workflow 的步骤是开发者写死的；Agent 的步骤是模型临场决定的 问一句：这一步是代码让它做的，还是它自己选的？
普通 Chatbot 底层都是同一个大模型 Chatbot 一轮结束就交卷，不调用工具改变外部状态，也不根据执行结果自我修正 它有没有「动手」并「看结果」？没有就是对话
脚本 / RPA 都能自动化完成任务 脚本靠规则处理可枚举的情况；Agent 处理的是开放、无法穷举路径的问题 能不能用 if-else 写清楚所有分支？能就别用 Agent
「更强的模型」 表现都变好了 换模型提升的是单次推理质量；做 Agent 提升的是任务完成的结构能力 变强的是脑子，还是工作方式？

不该用 Agent 的情况

  1. 任务路径可预测：能写成固定流程的，用 Workflow 或直接写脚本，更便宜也更可控。
  2. 结果无法验证：如果没有测试、没有客观反馈，Agent 就失去了纠错的锚点，错误会一路复合。
  3. 对可靠性要求极高且不允许人工介入：如无人值守的资金操作，自主性带来的不确定性难以接受。
  4. 成本敏感的简单任务：Agent 自主意味着多轮推理，token 消耗远高于单次调用。

8. 自测题（5 题）

Q1（定义）用一句话说清 Agent 和 Workflow 的区别。

判分要点：必须点出「控制权归属」——Workflow 由预定义代码路径编排，Agent 由 LLM 动态决定自己的流程和工具使用。只答「Agent 更智能/更自主」不给满分，因为没有说清差异的结构性来源。

Q2（机制）Agent 循环里，「环境反馈」这一步如果被拿掉，会发生什么？为什么？

判分要点：模型失去 ground truth，无法判断自己上一步做得对不对，只能凭自己的输出继续推理，于是错误不断累积（compounding errors），且可能陷入无效的自我循环。提到「无法纠错」「错误复合」任一即可得分。

Q3（机制）为什么 Anthropic 建议给 Agent 设置最大迭代次数这类停止条件？

判分要点：自主性带来两个副作用——成本随轮数线性上升、错误可能复合放大；停止条件和检查点是为了「维持控制」（maintain control）。

Q4（边界）团队想用 Agent 自动处理「每月固定的报表格式转换」，你会支持吗？

判分要点：倾向不支持。因为路径固定、规则明确，属于 Workflow 或脚本的适用场景；上 Agent 会引入不确定性和额外成本。能说出「能用 if-else 写清就不用 Agent」这句判断标准即可。

Q5（迁移）把「判断该不该用 Agent」的标准，套用到你自己的一个真实任务上，说明结论。

判分要点：开放式答案。合格标准是要明确列出：这个任务的步数是否可预知、有没有客观的成功判据、出错代价多大——三个维度中至少两个被讨论到。

10. 我的存疑点

  • Workflow 和 Agent 的边界在真实产品里是模糊的。市面上的 Agent 产品大多是两者的混合体：外层有固定编排，某些节点交给模型自由发挥。Anthropic 自己也把它们合称 agentic systems。所以我认为这个二分法更适合作为「设计时的思考工具」，而不是给产品贴标签的分类标准。
  • 「自主到什么程度才算 Agent」没有公认刻度。能调用 1 个工具和能调用 50 个工具、能跑 3 轮和能跑 300 轮，都叫 Agent。评价一个系统时，我觉得更有意义的问题是「它的自主度是否与任务的不可预测性相匹配」。
  • 文中提到自主性带来「复合错误」，但没给出量化的失效阈值。我暂时不知道多少轮之后错误率会显著上升，这可能高度依赖任务类型。
