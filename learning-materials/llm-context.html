大模型的上下文（Context）

一句话定义：模型在生成下一个字时，能「看见」的全部内容——它不是聊天的背景板，而是一份需要精打细算的有限预算。

2. 核心问题

  • 上下文窗口从 4K 涨到几十万 token，为什么「塞满」仍然是坏做法？
  • 「上下文工程」和「提示词工程」到底差在哪？是换了个说法吗？

3. 核心机制与组成

3.1 上下文里到底装了什么

Anthropic 对上下文的定义是：从大模型采样时所包含的那组 token。按 Claude 官方课程的拆解，一次请求里模型能看到的包括：

组成说明谁把它放进去的
系统提示角色设定、规则、输出格式要求开发者（固定）
对话历史之前所有轮次的 user / assistant 消息累积
工具定义可用工具的 schema 与说明，本身就占 token开发者（固定）
工具返回结果搜索结果、文件读取内容、命令输出运行时
外部数据 / 检索结果RAG 召回的文档片段运行时
附件与 Skill 内容上传的文件、被触发时加载的 SKILL.md按需
思考块（thinking）模型自身的推理过程（部分产品可见）模型

关键点：上下文是「每一次 API 调用的输入」，进去收费、出来也收费。它不是一份持久化的档案。

3.2 为什么上下文是稀缺资源

Anthropic 在《Effective context engineering for AI agents》里给了两条架构层面的原因：

  1. 注意力的 n² 压力：Transformer 架构让每个 token 都能关注到其他所有 token，n 个 token 产生 n² 组成对关系。上下文越长，模型捕捉这些关系的能力被摊得越薄。
  2. 训练分布偏向短序列：模型在训练时见到的短序列远多于长序列，因此对「跨越整段上下文的依赖关系」经验更少、专用参数更少。位置编码插值等技术能支持更长序列，但会牺牲一部分位置理解精度。

结果是所谓 context rot（上下文腐烂）：随着上下文 token 数增加，模型准确回忆其中信息的能力下降。这是性能梯度，不是硬悬崖——模型在长上下文下依然能干活，只是检索精度和长程推理的可靠度下降。

3.3 从提示词工程到上下文工程

Anthropic 的表述是：上下文工程是提示词工程的自然演进。差别在于——提示词工程关注怎么写好一段提示（尤其是系统提示），是一次性的离散任务；上下文工程关注在推理全程持续策展最优 token 集合，是每次决定「给模型看什么」时都要做的迭代动作。它管理的范围包括系统指令、工具、MCP、外部数据、消息历史等所有可能落进上下文的东西。

指导原则一句话：用尽可能小的高信号 token 集合，最大化达成期望结果的概率。

4. 最小心智模型

类比：上下文是工人的「工作台」，不是他的「仓库」。

工人一次能摊开在工作台上的图纸、零件和便签是有限的。台面堆得越满，他找东西越慢、越容易拿错零件；真要用某个零件，正确做法是需要时再从仓库取，而不是一开始就把整个仓库倒上台面。

而且下班时工作台会被清空——明天开工，台面上什么都没有。这就是为什么 Agent 需要「外部记忆」这类机制。

5. 我的理解

（本人改写，非 AI 原文）

类比：上下文像模型的「当下视野」，记忆才是它的「履历」。一个人视野里能同时盯住的东西有限，视野边缘的东西他会看见但看不真切；而他昨天做过什么，靠的是记事本，不是靠此刻的视野。

大白话：上下文 = 这一次调用时，摆在模型面前的全部文字。它决定了模型「此刻知道什么」，也直接决定了你要花多少钱、等多久。

它其实不是：

  • 不是「窗口越大越好」。窗口大只是「不容易直接失败」，不等于「信息都被有效利用」。堆满低信号内容反而会稀释注意力，这就是 context rot。
  • 不是「聊天记录 = 记忆」。对话历史超出窗口后会被压缩或截断，被压缩掉的部分模型是真的看不到了。要跨会话保留信息，必须写进外部存储（文件、数据库、memory 工具）。
  • 不是免费的资源。每一个 token 都要付钱、都要占用延迟，稳定的大块内容（系统提示、工具定义）值得用 prompt caching 复用。
  • 不是「提示词换个说法」。提示词关心措辞，上下文工程关心取舍——放什么、不放什么、什么时候放。我觉得这个区分是本篇最有价值的一点。

6. 具体应用场景

场景：长任务编码 Agent 的上下文管理

Claude 官方课程给出的例子是合规审查 Agent：它不会把整本建筑规范塞进系统提示，而是在需要某一条时调用 lookup_building_code 工具去查。这就是四种策略里的「按需加载 / just-in-time」。

维度内容
谁在用需要连续工作几十分钟到数小时的 Agent 产品（编码、研究、运维）
具体怎么用项目说明文件（如 CLAUDE.md）常驻系统提示；具体文件内容用 glob / grep 在需要时才读取；对话接近窗口上限时自动压缩历史；跨会话的用户偏好写入 memory 目录
为什么非它不可Agent 跑得越久，产生的数据越多（工具结果、报错、历史轮次），全量保留必然撑爆窗口；而一旦窗口满了请求直接失败，任务前功尽弃
效果怎么衡量任务完成率、平均 token 消耗、缓存命中率、压缩后关键信息的保留率

我自己的一个实例：这个仓库里的 SKILL.md 只有在被触发时才会被读进上下文，平时模型只知道它的 name 和 description（约几十个 token）。这正是「渐进式披露」——需要时才把细节搬上工作台。如果我一次性把十几个 Skill 的全文都塞进去，上下文会立刻被无关内容占满。

7. 易混淆概念与使用边界

混淆对象表面相似点本质区别判断口诀
上下文 vs 记忆 都关系到模型「知道什么」 上下文是单次调用的输入，用完即走；记忆是写在窗口之外的持久化存储，需要时再取回 问：会话结束后它还在吗？不在就是上下文
上下文工程 vs 提示词工程 都在优化模型的输入 提示词工程关注「怎么写好这段指令」（离散任务）；上下文工程关注「全程维持最优 token 集合」（迭代策展），范围含工具、历史、外部数据 问：你改的是措辞，还是改的是「放什么进来」？
长上下文 vs RAG 都用于让模型接触外部知识 长上下文是把材料全放进窗口；RAG 是检索出最相关的片段再放。前者成本高且受 context rot 影响，后者更省但依赖检索质量 不是二选一，而是「按需加载」往往更划算
上下文 vs 模型知识 都能让模型答对问题 上下文里的信息是当次提供的；模型知识来自训练参数。放进上下文不等于模型「学会了」 下次新会话它还记得吗？不记得说明只是上下文

使用边界（不该怎么做）

  1. 不要把整个知识库塞进窗口。成本、延迟、context rot 三重代价，回报却是递减的。
  2. 不要用长上下文替代检索。窗口大是兜底能力，不是让它当数据库用。
  3. 不要忽视缓存。系统提示和工具定义这类稳定大块内容应该被缓存复用，否则每次调用重复付费。
  4. 不要把敏感信息随手放进上下文。上下文内容会被模型看到，也可能进入日志；密钥、密码、个人信息都不该出现在里面。
  5. 不要指望模型自己「记住」被压缩掉的内容。压缩是有损的，真正重要的信息要显式写进外部笔记。

8. 自测题（5 题）

Q1（定义）列出一次 LLM 调用中上下文包含的五类内容。

判分要点：系统提示、对话历史、工具定义、工具返回结果、外部/检索数据、附件与 Skill 内容、思考块——答出任意五类即可。只答「聊天记录」不给满分。

Q2（机制）为什么上下文变长后，模型表现会下降？说出两条架构层面的原因。

判分要点：① Transformer 的 n² 成对关注关系被摊薄；② 训练数据中短序列占多数，模型对长程依赖经验不足（位置编码插值也带来位置理解损失）。答出任一得一半，答全满分。

Q3（机制）context rot 是「硬悬崖」还是「性能梯度」？这个区别有什么实践意义？

判分要点：是性能梯度——模型在长上下文下仍可用，只是检索精度和长程推理可靠性下降。实践意义：不能因为「窗口没满」就放心堆料；也不能把长上下文当成不可用，而应配合策展策略使用。

Q4（边界）有人说「等模型支持 1000 万 token 上下文，RAG 就没用了」，你怎么回应？

判分要点：不认同。窗口大小解决的是「能不能装下」，RAG / 按需加载解决的是「该不该装进去」——成本、延迟、context rot 都随长度恶化。而且窗口满了请求直接失败，不代表装得越多效果越好。能说出「最小高信号 token 集合」原则即可。

Q5（迁移）你正在做一个要跑 2 小时的 Agent，列出你会采用哪几种上下文管理策略，以及各自的理由。

判分要点：开放题。合格标准：至少提到按需加载（避免塞满）、压缩（应对长度增长）、外部笔记（跨轮次保留关键信息）、子智能体隔离（控制主上下文污染）中的两项，并说明对应解决的是成本、窗口还是记忆问题。

10. 我的存疑点

  • context rot 的量化阈值我还没找到。Anthropic 只说「所有模型都有这个特性，只是斜率不同」，没有给出「多少 token 之后明显恶化」的通用数字。我猜这个阈值高度依赖任务类型（检索 vs 推理）和内容密度，不能一概而论。
  • 压缩（compaction）到底丢了什么，很难验证。官方文档建议「先最大化召回，再迭代提升精确度」，但实际操作中没有客观指标判断某次压缩是否丢掉了后面要用到的关键信息。这是我觉得上下文工程里最工程化、也最依赖经验的一环。
  • 「上下文」这个词本身有歧义。它有时指 context window（容量上限），有时指当次输入的内容，有时在语言学里指语境。读中文资料时经常混淆，我在本资料里统一取「当次调用的输入 token 集合」这一含义。
