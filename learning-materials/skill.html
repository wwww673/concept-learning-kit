  3. 能判断一个工作流该封装成 Skill、还是写进 CLAUDE.md 或直接提问。

2. 核心问题

  • 为什么要做成文件夹，而不是一段更长的提示词？
  • 装了几百个 Skill，为什么不会撑爆上下文？

3. 核心机制与组成

3.1 一个 Skill 长什么样

Anthropic 官方定义：Skill 是模块化能力，每个 Skill 打包了指令、元数据和可选资源（脚本、模板），Claude 在相关时自动使用。最小形态就是一个目录加一个 SKILL.md：

my-skill/
├── SKILL.md          # 必需：YAML 元数据 + Markdown 正文
├── REFERENCE.md      # 可选：详细参考，按需才读
├── FORMS.md          # 可选：特定场景的补充指南
└── scripts/
    └── helper.py     # 可选：可执行脚本，运行它不等于读它

SKILL.md 由两部分组成：

---
name: concept-study-guide
description: 为一个新概念生成结构化的个人学习资料……当用户说"学习某个概念"时使用。
---

# 正文
## 适用场景
## 输入信息
## 生成步骤
……

两个字段各司其职：name 决定它叫什么（也是调用时的命令名），description 决定它什么时候被触发——模型启动时只看得到这两个字段，然后拿它们跟当前任务做语义匹配。所以 description 写不好，Skill 就永远不会被用上。这是官方文档反复强调的一点。

3.2 三级渐进式披露

3.3 它解决了 Agent 的什么缺口

Anthropic 在《Equipping agents for the real world with Agent Skills》里给出的判断是：Agent 缺的不是智力，而是领域专长（expertise）。他们的原话大意是——报税时你愿意找数学天才从第一性原理推导，还是有经验的老会计？多数人选后者，不是因为后者更聪明，而是因为他有积累下来的经验。

Skill 就是把这个「积累下来的经验」打包成 Agent 能读取的形式。与提示词的关键差别：提示词是对话级的一次性指令，Skill 是可复用、按需加载、能被版本管理的文件资源。

4. 最小心智模型

类比：给新员工准备的入职手册，放在公司书架（文件系统）上。

新人入职时不需要背下整本手册。他只需要知道「书架上有哪些手册、各自管什么」；真到要报销时，才去抽《报销流程》那一本翻；手册里附的脚本，他直接跑就行，不必把代码背下来。

更关键的是：手册写一次，所有新人都受益，还能用 Git 版本管理和团队共享。而提示词相当于每次都在微信里重新打字交代一遍。

5. 我的理解

（本人改写，非 AI 原文）

类比：Skill 就是把「我第 N 次粘贴进聊天框的那段提示词」，做成一个带说明书的工具箱。区别在于：粘贴的提示词会随会话消失，而工具箱放在文件系统上，谁都能拿、还能改、还能提交到 Git。

大白话：Skill = 一个文件夹 + 一份带 name/description 的 SKILL.md + 可选的脚本和参考资料，模型在觉得相关时自己去翻。

它其实不是：

  • 不是「更长的提示词」。本质差别在于存储位置和加载时机：提示词活在对话里、一次性；Skill 活在文件系统里、可复用、按需分级加载。
  • 不是 MCP 的替代品。我的记法是：MCP 解决「连不连得上」，Skill 解决「会不会做」。一个给工具，一个给方法。两者是互补关系，官方文档也说 Skill 可以教 Agent 如何组合使用 MCP 提供的能力。
  • 不是「一调用就把全文塞进上下文」。只有元数据常驻；正文命中才读；脚本甚至只运行不读取。这一点是它和「把长指令写进 CLAUDE.md」最大的不同——CLAUDE.md 是常驻的，Skill 不是。
  • 不是程序员的专利。文件是通用载体，产品、运营、财务都能把自己的流程写成 Skill。

6. 具体应用场景

场景：把「生成概念学习资料」这件事固化成本仓库的 Skill

这就是本次作业做的事，也是我能举出的最真实的例子。

维度内容
谁在用我自己（以及任何克隆这个仓库、在 WorkBuddy / Claude Code 中打开它的人）
具体怎么用Skill 放在 .workbuddy/skills/concept-study-guide/，作为项目级 Skill 随仓库走；我说「用 concept-study-guide 学一下向量检索」，它就按 SKILL.md 里的十节结构产出一份 HTML
为什么非它不可如果我每次都重新打字描述「要十节、要来源、要自测题」，既会遗漏也会走样；固化成 Skill 后，换任何概念都能得到同质量的产出，而且这份方法论本身可以用 Git 迭代
效果怎么衡量换一个陌生概念时是否无需修改提示词即可复用；产出资料是否稳定包含全部十节；来源是否都可核查

官方给的另一类例子是品牌规范 Skill：把公司的配色、字体、Logo 用法和 PPT 模板脚本打包，让 Agent 每次做出来的幻灯片都符合规范——这类「组织知识沉淀」是 Skill 最典型的企业用途。

7. 易混淆概念与使用边界

混淆对象表面相似点本质区别判断口诀
Prompt（提示词） 内容都是给模型的指令 Prompt 是对话级、一次性、每次要重贴；Skill 是文件级、持久、自动发现并按需加载 这段指令你会用第二次吗？会就做成 Skill
MCP 都被说成「扩展 Agent 能力」 MCP 提供连接与工具（能访问什么系统）；Skill 提供方法与流程（怎么把事做对） 是让它「够得着」，还是「会做」？
CLAUDE.md / 项目说明文件 都是项目里的 Markdown，都写约定 CLAUDE.md 内容常驻上下文，适合事实型约定（技术栈、目录结构）；Skill 按需加载，适合流程型长内容 内容是「事实」还是「步骤」？步骤长的放 Skill
Subagent（子智能体） 都涉及任务分工 Subagent 是独立上下文的执行者；Skill 是知识包。两者可组合：子智能体也可以加载 Skill 是一个「干活的人」还是一本「手册」？
微调（Fine-tuning） 都能让模型在某个领域表现更好 微调改变模型权重，成本高、不可逆；Skill 只改变上下文，改一行就生效 改的是脑子，还是给的手册？

不该用 Skill 的情况

  1. 一次性任务。只做一回的事，直接说即可，封装成 Skill 是浪费。
  2. 一两句话能说清的约定。这类更适合写进项目说明文件常驻，而不是做成一个按需加载的 Skill。
  3. 内容依赖实时数据。Skill 是静态文件，本身不会自动更新；要拿实时信息必须配合工具或 MCP。
  4. 来源不明的第三方 Skill。官方明确警告：Skill 可以包含可执行代码，恶意 Skill 可能引入漏洞或导致数据外泄。只从可信来源安装，装前通读它打包的文件。
  5. 把密钥硬编码进 Skill。官方安全建议明确列出这一点——敏感信息不应写进 Skill 文件。

8. 自测题（5 题）

Q1（定义）SKILL.md 的 YAML 前置元数据里，name 和 description 分别起什么作用？哪个更关键？

判分要点：name 是技能标识（也是调用命令名）；description 决定模型判断「何时该用它」。description 更关键——它写不好，Skill 就不会被触发。官方文档明确说模型用 name 和 description 来决定是否响应当前任务。

Q2（机制）装了 100 个 Skill，为什么上下文不会被撑爆？

判分要点：启动时只加载每个 Skill 的元数据（约 50–100 tokens）；正文在匹配命中后才读取（建议 < 5k tokens）；附属资源和脚本在被引用时才访问，脚本甚至可以只执行不读入。这就是渐进式披露。

Q3（机制）为什么 Skill 里放可执行脚本，比把代码写进 Markdown 正文更省上下文？

判分要点：脚本由模型通过命令执行，代码内容不必进入上下文；而写进正文的代码会被当作 token 读入。同时脚本提供确定性操作，比让模型每次重新生成代码更可靠。

Q4（边界）你有一段「代码评审检查清单」，该写成 Skill 还是放进项目说明文件？

判分要点：倾向写成 Skill——它是流程型、内容较长、只在评审时才需要的知识，按需加载更省上下文；项目说明文件适合放常驻的事实型约定。能说出「长且非每次都需要 → Skill」的判断依据即可得分。

Q5（迁移）挑一件你每周重复做、且每次都要重新交代 AI 的事，描述你会怎么把它写成 Skill（列出目录结构和 description）。

判分要点：开放题。合格标准：① 目录里至少包含 SKILL.md；② description 里既写了「做什么」也写了「什么时候用」；③ 能说清哪些内容放正文、哪些拆到附属文件。三点齐全为满分。

10. 我的存疑点

  • 触发完全依赖 description 的语义匹配，这点我觉得是最大隐患。官方文档也承认，如果 description 写得不好，Skill 就不会被调用，而开发者很难预判模型会怎么匹配。实践中我的应对是把「用户可能怎么开口」的原话写进 description（比如本 Skill 里就写进了「用这个 Skill 学 XX」这类说法），但这仍是经验而非方法。
  • 「该拆成几个小 Skill 还是一个大的」，标准模糊。官方建议「保持专注、为不同工作流创建单独的 Skill」，但也说多个 Skill 可以自动组合。我的判断是：按「是否会被同时用到」来划分——会同时用到的放一起，互斥的拆开。但这条是我自己归纳的，没有官方文档背书。
  • Skill 的「版本管理」目前比较原始。它本质是文件夹，改了就改了，缺少依赖声明和兼容性检查（官方只提供了可选的 dependencies 字段）。这对团队协作是个隐患。
