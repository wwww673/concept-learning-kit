概念关系说明：Agent × 上下文 × Skill

Agent 是干活的主体，上下文是它此刻能看到的全部信息，Skill 是它按需取用的经验手册。三者构成一个闭环。

配套学习资料：Agent · 大模型的上下文 · Skill ｜ 完整文字版见仓库 docs/concept-relationship.md

1. 三者分别回答什么问题

概念回答的问题本质存在形态
Agent谁来把这件事做完？一种系统结构：模型 + 工具 + 循环 + 反馈运行时的执行循环
上下文它此刻能看到什么？一种有限资源：本次调用的输入 token 集合每次 API 调用的输入
Skill它凭什么做得专业？一种知识封装：文件夹 + 元数据 + 指令 + 脚本文件系统上的静态文件

值得注意：三者的存在形态完全不同——一个是运行时循环，一个是每次调用的输入，一个是磁盘上的文件。它们不在同一个层面，这也是很多人把它们混为一谈的原因。

3. 上下文如何影响 Agent 的工作

这是三条关系里最容易被低估的一条——上下文不是 Agent 的背景板，而是它的能力边界。

3.1 决定 Agent 知道什么

Agent 没有独立于上下文的记忆。它每一步能依据的，只有当前上下文里摆着的东西。上下文里没有的信息，对 Agent 而言等同于不存在。所以换一个更长的窗口不等于让它更聪明，但在正确时刻塞进正确的信息，判断质量会立刻提升。

3.2 决定 Agent 注意什么

由于注意力的 n² 压力与 context rot 的存在，堆在上下文里的低信号内容会挤占高信号内容的注意力。对 Agent 的直接影响是：随着循环轮数增加，工具返回的原始结果不断累积，模型反而容易忽略最初的任务目标。这就是长任务 Agent 必须做压缩的原因——首先不是为了省 token，而是为了不让 Agent 失焦。

3.3 决定 Agent 能跑多久

管理手段解决的问题对 Agent 的意义
按需加载避免一开始就撑满能启动，且上下文保持高信号
压缩长度随轮次增长能跑得久
外部笔记跨轮次保留关键信息能保持目标感，不半途忘掉初衷
子智能体隔离探索过程的污染主上下文只留结论，专注综合判断

4. Skill 如何沉淀可复用的任务知识

沉淀的是什么

Agent 有智力和工具，但缺领域专长——也就是「这件事的正确做法」。Skill 沉淀的正是这部分，而且不止「怎么做」，还包括「什么时候做」和「做到什么程度算合格」。我的 concept-study-guide 里就同时写了这三层：适用场景、生成步骤、自检清单。少任何一层，复用时都会出问题。

为什么能沉淀很多却不拖累 Agent

级别内容加载时机上下文开销
L1 元数据name + description始终每个约 50–100 tokens
L2 指令正文SKILL.md 主体匹配命中后建议 < 5k tokens
L3 资源与代码参考文档、脚本、模板被引用时脚本可执行、不必读入

这是 Skill 与「把长指令写进项目说明文件」的根本区别：后者常驻上下文，写多少占多少；Skill 平时只占几十个 token。所以一个 Agent 可以装备几百个 Skill 而不影响性能——知识可以无限沉淀，代价却按需支付。

沉淀是一个闭环

做任务 → 发现反复交代同样的要求 → 抽成 Skill → 用几次发现问题 → 改 SKILL.md → 提交 Git → 下次自动生效

这条最有价值的地方在于：上下文会清空，模型权重不会因为你改了个流程而改变，但 Skill 会。它是 Agent 时代少数能让「经验」真正跨会话累积的机制。

5. 用本次作业走一遍闭环

阶段发生了什么对应概念
1创建 concept-learning-kit 仓库，git init—
2把「怎么学一个概念」写成 .workbuddy/skills/concept-study-guide/SKILL.mdSkill（方法固化成文件）
3说「用 concept-study-guide 学 Agent」，模型读到 description 匹配成功，把正文读进上下文Skill → 上下文（①）
4按步骤检索来源、搭骨架、生成 HTML；期间用搜索工具找来源、用命令验证链接上下文 → Agent → 工具（③④）
5验证链接返回 200/404、curl 报「端口 22 被拒」，结果进入上下文，模型据此改用 HTTPS环境 → 上下文（②）
6三份 HTML 交付；把「来源必须验证」写进 Skill 自检清单，提交 Git交付物 → Skill（⑥）

最直观的一点：同一个模型，因为上下文里多了一份 SKILL.md，产出从「一段解释」变成了「一份结构完整、带来源、带自测题的学习资料」。模型没变，变的是上下文；而让上下文变好的，是 Skill。

6. 我的判断

  1. 上下文工程比提示词工程更接近 Agent 开发的核心，因为表现上限取决于每一步看到什么。但要知道「哪些内容值得进来」，恰恰需要 Skill 提供——所以我认为 Skill 是上下文工程的关键抓手。
  2. 三者的重要性随任务复杂度变化。简单任务里 Skill 作用最大；长任务里上下文管理会迅速超过一切——跑不完的任务，方法再好也没用。所以不存在「哪个更重要」的静态答案。
  3. Agent 与 Workflow 的二分法在实践中是模糊的，真实产品几乎都是混合体。这个划分更适合作为设计时的思考工具，而非贴标签的分类标准。
  4. Skill 目前最大的短板是触发不可控，完全依赖 description 的语义匹配。（这是我自己的推测，无官方资料支持。）未来可能需要更结构化的触发条件。
一句话记忆法：Agent 是工人，上下文是他的工作台，Skill 是书架上的手册。工作台大小有限，不能什么都往上堆；手册可以放几百本，因为只有需要时才抽出来翻；而工人干活的经验，最后又会写回手册里。
